Customer Support Product

Support for TeddyBed, run entirely inside the company database. A ticket is a task on one board — every channel is just a different way of creating one. Zero new tables.

Status: planned 5 PRs Operators: Daniel & Carla Plan: docs/plans/customer-support-product.md

The one design decision

Every channel writes the same shape into tasks.metadata. Ticket numbers come from a sequence, not a table. A matching people.email links the ticket to the customer's existing record — same join key the Shopify sync uses.

{
  "channel":        "web_form" | "email" | "manual",
  "customer_email": "jane@example.com",
  "customer_name":  "Jane Doe",
  "ticket_no":      "TD-1042"
}

The PRs

Each one independently shippable and verified before the next starts. PR 1 is the usable v1 — everything after it is intake automation.

1

Seed board + support view + manual intake

Migration seeds the Support board, four columns, and the ticket-number sequence. /admin/support wraps the existing board machinery: customer email on the card, comment thread front and center, a "New ticket" form.

Verify: ticket for a known + unknown email · drag through all four columns · stage log records moves · existing boards untouched.
2

Scoped logins for Daniel & Carla

admins.role column: support sees only /admin/support, gated server-side in the layout. Two admin rows + board membership. Magic-link login already exists — zero new auth code.

Verify: support role renders /admin/support · /admin/revenue and /admin/contacts redirect · Dave's login unchanged.
3

Public endpoint + Teddy site form

POST /api/support — validated, rate-limited, honeypot, CORS for teddybed.com.au. Same helper as everything else. Small embeddable form for the Shopify theme.

Verify: allowed vs. disallowed origins · honeypot silently drops · submission appears in New within seconds.
4

Email ingest

Gmail forwarding rule → Resend inbound → webhook. Replies thread onto the open ticket via the [TD-1042] subject token or sender match; everything else opens a new ticket. Idempotent on message id. No Gmail API, no OAuth, no token-refresh cron.

Verify: fresh email → new ticket · reply → comment on same ticket · webhook replay → no duplicates.
5

Reply from the admin later

Outbound replies via Resend from the task drawer, token in the subject so PR 4 threads the response. Carla never opens Gmail. Deferred until the first four prove themselves in use.

Assumptions — said out loud

  • Scoped access for Daniel & Carla, not the full admin. If full access is fine, PR 2 shrinks to two INSERTs.
  • Website form lives on the Shopify storefront, posting cross-origin here. If not, only the CORS allowlist changes.
  • Support email is Google-hosted — forwarding rule beats OAuth polling.

Not building

  • SLA timers, canned responses, CSAT surveys
  • Auto-assignment or tagging taxonomy
  • Customer-facing ticket portal
  • A support_tickets table

Definition of done

Carla logs in with a magic link, sees only the Support board, and works tickets that arrived from the website and the support inbox — with each customer's full history one click away, because the ticket links to the same people row as their Shopify orders. Single source of truth, zero new tables.
